# 测试驱动开发

TDD 就是红 → 绿的循环。本技能是让这个循环产出**值得保留的测试**的参考：什么算好测试、测试放在哪里、反模式，以及循环的规则。每一节在每一轮都适用：在循环前和循环中查阅，而不是事后。

探索代码库时，读一下 `GLOSSARY.md`（如果存在），让测试命名与接口词汇和项目的领域语言一致；并遵守你正在改动区域的 ADR。

## 什么算好测试

测试通过**公共接口**验证行为，而不是实现细节。代码可以彻底重写，测试不应随之改变。好测试读起来像一份规格：“用户可以用有效购物车结账”直接说明存在什么能力，而且它不在乎内部结构，所以能扛住重构。

示例见 [tests.md](tests.md)，打桩（mocking）原则见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝**（seam）是你测试时所在的公共边界：在不深入内部的前提下观察行为的接口。测试只落在接缝上，绝不针对内部实现。

**只在预先约定的接缝上测试。** 写任何测试之前，先写下要测的接缝并与用户确认。没有确认的接缝不写测试。你不可能测遍一切，所以事先约定接缝，才能把测试精力落在关键路径与复杂逻辑上，而不是每个边界情况。

要问：“公共接口是什么，我们应该测哪些接缝？”为每个提议的接缝写一句说明：它能抓住什么、漏掉什么。

当接口本身的形状存在疑问时（模块有多深、接缝该在哪、接口该暴露什么），调用 `codebase-design` 技能获取词汇。它是模块、接口、深度、接缝、适配器、杠杆与局部性的共享定义来源，是查阅用的参考，不是要跑的一轮会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（不用接口而直接查数据库）。特征是：行为没变，重构却让测试挂了。
- **同义反复**：断言用和实现一样的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工用同样方式得出的快照、把常量断言为它自己），于是它按构造必然通过，永远不可能与代码不一致。期望值必须来自独立的事实来源：已知正确的字面量、手算过的例子、规格。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是**想象中**的行为：你测的是事物的**形状**而非用户可见行为，测试对真实变化不敏感，而且在理解实现之前就锁死了测试结构。应改为**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是一颗**曳光弹**，根据上一轮学到的东西调整。

## 循环的规则

- **先红后绿。** 先写失败的测试，再只写足够让它通过的代码。不要预判未来的测试，也不要加投机性的功能。
- **一次一个切片。** 每轮一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于审查阶段（见 `code-review` 技能），不属于红 → 绿实现循环。
