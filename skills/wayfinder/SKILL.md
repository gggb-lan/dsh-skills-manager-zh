一个模糊的想法来了，大到装不进一个代理会话，而且被迷雾包裹：从这里到**目的地**的路还看不见。Wayfinding 是去找那条路，不是冲着目的地猛冲。本技能把路线画成仓库 issue 跟踪器上的**共享地图**，然后逐个处理它的**决策工单**（答案是决策、不是待执行的构建切片的工单），直到路线清晰。

目的地因事而异，而命名它是测绘的第一个动作：它塑造每一个工单。目的地可能是一份交接并持续迭代的规格、一个在规划开始前就要锁定的决策，或一处就地完成的改动（比如数据结构迁移）。地图与领域无关：工程、课程内容、任何符合这个形状的事都行。

## 只规划，不施工

Wayfinder 默认是**规划**：每个工单落定一个决策，地图在路线清晰时完成——在有人去真正动手之前，没有遗留待决事项。想去直接干活的冲动，通常就是“你已经走到地图边缘、该交接了”的信号。某次工作可以在它的**Notes** 里覆盖这一点，把执行也纳入地图；但没有这个覆盖时，产出决策，不产出交付物。

## 用名字指代

每张地图、每个工单都是一个 issue，所以它有一个**名字**：标题。在所有给人看的内容里（叙述、地图的“目前决策”），用名字指代它，绝不用裸 id、编号或 slug。`#42, #43, #44` 堆一墙是读不了的；名字一眼可读。id 和 URL 不会消失：名字包住链接，但它们**在名字内部**，从不替代名字。

## 地图

地图是本仓库 issue 跟踪器上的一个 issue，打 `wayfinder:map` 标签，是权威产物。它的工单是地图的子 issue。

地图是**索引**，不是仓库。它列出已做的决策，并指向持有细节的工单；一个决策只活在一个地方——它的工单——所以地图从不复述，只做摘要并链接。

**地图、子工单、阻塞关系、前沿查询在物理上存在哪里，取决于跟踪器。** issue 跟踪器应当已经提供给你。如果没有，提示用户运行 `setup-matt-pocock-skills`。查阅跟踪器文档的 “Wayfinding operations” 一节，了解**这个**仓库如何表达它们。如果没有提供任何跟踪器，默认使用本地 Markdown 跟踪器。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。未关闭的工单**不**列出：它们是未关闭的子 issue，靠查询找到。

```markdown
## 目的地

<走到这张地图尽头是什么样子：这次工作要找的路通向的规格、决策或改动。一两行；每个会话在选工单前先对齐它。>

## 说明

<领域；每个会话都该查阅的技能；这次工作的常设偏好>

## 目前决策

<!-- 索引：每个已关闭工单一行，够判断相关性即可，然后点链接展开工单里的细节 -->

- [<已关闭工单标题>](链接)：<答案的一行摘要>

## 尚未明确

<!-- 见“战争迷雾”：在范围内、但还无法开工单的迷雾；随前沿推进逐块毕业 -->

## 不在范围内

<!-- 见“不在范围内”：被判为超出目的地的工作；关闭，永不毕业 -->
```

### 工单

每个工单是地图的**子 issue**；跟踪器的 issue id 就是它的身份。正文就是那个问题，规模控制在一个 100K token 的代理会话内：

```markdown
## 问题

<这个工单要落定的决策或调查>
```

每个工单带一个 `wayfinder:<type>` 标签，取值 `research`、`prototype`、`grilling`、`task`（见[工单类型](#工单类型)）。`wayfinder:` 标签是地图及其工单唯一携带的标签，绝不打 `ready-for-agent` 这类分诊标签：它们是决策，不是实现工作。

会话**认领**工单的方式是把它指派给驱动地图的开发者，并且要在任何工作**之前**做，这样并发的会话会跳过它。这个指派**就是**认领：未关闭且未指派的工单即未被认领。

阻塞关系使用跟踪器的**原生**依赖关系：这很关键，因为它能在跟踪器自己的 UI 里把前沿**可视化**出来，人不用打开地图就知道哪些可以拿。只有缺少原生阻塞的跟踪器才退回正文约定。当所有阻塞它的工单都关闭时，工单**解除阻塞**；**前沿**是未关闭、未阻塞、未被认领的子工单——已知世界的边缘。

答案不是正文的一部分；它在落定时被记录（见[在地图上推进](#在地图上推进)）。解决工单时产生的资产从 issue 链接过去，不要粘贴进去。

## 工单类型

每个工单要么是 **HITL**（human in the loop，和代表自己的真人一起做），要么是 **AFK**，由代理独立驱动。HITL 工单只能通过那场实时交流落定；代理绝不代替人类那一侧（一个自问自答的追问代理已经破坏了这一条）。

- **Research**（AFK）：读文档、第三方 API，或本地知识库等资源，挖出某个决策正等着的事实。由子代理调用 `research` 技能解决。需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：做一个便宜、粗糙、具体的产物来提升讨论的保真度（提纲、草稿、桩、UI/逻辑代码），调用 `prototype` 技能。把原型作为资产链接。当关键问题是“它该长什么样”或“它该怎么表现”时使用。
- **Grilling**（HITL）：对话。默认情况。总是调用两次技能：`grilling` 与 `domain-modeling`。
- **Task**（HITL 或 AFK）：在能做**决策**之前必须完成的手工工作：没什么可决策、可原型、可调研，但讨论要等它做完才能继续。注册某个服务以便判断它的 API、开通访问权限、搬数据以便看清它的形状。这是唯一“做”而不是“决策”的类型，它的价值在于解锁一个决策，而不是交付目的地。能独立完成就由代理做（AFK）；否则给人类一份精确清单（HITL）。工作完成即落定；答案记录做了什么以及后续工单依赖的事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图是**刻意**不完整的：还看不见的东西不要画。在活跃工单之外是**战争迷雾**：你能感觉到要来、但还钉不住的决策与调查，因为它们挂在仍未关闭的问题上。解决一个工单会清掉它前方的迷雾，把现在能明确的东西一块块毕业成新工单，直到通往目的地的路清晰、不再有工单。

地图的**尚未明确**一节就是记录那种朦胧视野的地方：怀疑存在的问题、以后要回访的区域。它是**朝向**目的地的未探索前沿：这里的一切都在范围内，只是还不够锐利到能开工单。视野允许多模糊就写多模糊，写多全就写多全；它同时是给协作者的指示牌，说明这次工作要往哪走。

**迷雾还是工单？** 判据是“你现在能不能把问题**说清楚**”，而**不是**“你现在能不能回答它”。

- **开工单**：问题已经足够锐利，即使它被阻塞、你现在动不了。
- **写进尚未明确**：你还无法那么锐利地表述。不要把迷雾预先切成工单大小：它比工单更粗，等前沿推到它时，一块可能毕业成好几个工单，也可能一个都不毕业。

**尚未明确**不包含已经决定的（目前决策）、已经是活跃工单的、以及不在范围内的（下一节）。

## 不在范围内

迷雾只会朝目的地聚拢。目的地固定了范围，所以超出它的工作是**不在范围内**：它不是迷雾，也不属于**尚未明确**。它在地图上拥有自己的**不在范围内**一节：你有意识地从**这次**工作中排除掉的工作。决定它在这里的是范围，不是锐利度。

不在范围内的工作永不毕业（前沿在目的地处停止），所以只有当目的地被重画时它才会回来，而且是作为一次全新的工作，不是续做。

把某件事判出范围是一次定范围的动作，不是路线上的一个步骤。当一个已存在的工单发现其实在目的地之外（测绘时误纳入，或被某个结论暴露），**关闭它**（关闭的工单明确不在前沿），并在**不在范围内**留一行：摘要加排除理由，链接那个已关闭工单。它不进入**目前决策**，那里记录的是真正走过的路线；范围边界不是路线上的步骤。

## 调用方式

两种模式。无论哪种，**每个会话绝不解决超过一个工单**，研究工单除外。

### 绘制地图

用户带着一个模糊想法来调用。

1. **命名目的地。** 调用两次技能：`grilling` 与 `domain-modeling`，钉住这张地图要通向什么：规格、决策还是改动。目的地固定范围，所以先落定它。
2. **测绘前沿。** 再次追问，这次**广度优先**：在整个空间上铺开，而不是在任一线程上深入，浮出开放决策和现在就能走的第一步。**如果这没有浮出迷雾**（到目的地的路已经清楚，整段旅程小到一个会话能装下），你不需要地图。停下来问用户想怎么推进。
3. **创建地图**（标签 `wayfinder:map`）：填好目的地与说明，目前决策留空，把迷雾草绘进**尚未明确**。
4. **创建现在就能明确表述的工单**，作为地图的子 issue，然后**第二遍**再连阻塞边（issue 需要先有 id 才能互相引用）。这一遍同时写交叉引用，用真实 id：占位符 `#<n>` 会自动链接到无关 issue。连线把它们分成前沿与被阻塞；还无法明确的都留在迷雾里，即**尚未明确**一节。
5. **放出研究子代理。** 对刚创建的每个 `research` 工单，起一个子代理调用 `research` 技能并行解决，把发现落在一次性的 `research/<name>` 分支上，并从工单给出上下文指针。推分支但不提 PR：它永不合并。
6. 停止：测绘就是一个会话的工作；它本身不落定任何东西。

### 在地图上推进

用户带着地图（URL 或编号）来调用。工单是**可选**的：不给工单时，由你挑下一个决策，而不是用户。

1. 加载**地图**：低分辨率视图，不是每个工单的正文。
2. 选工单。用户点名就用它；否则按顺序取第一个前沿工单。**认领它**：做任何工作之前先指派给自己。
3. 按它的 `wayfinder:<type>` 标签指明的类型解决（见[工单类型](#工单类型)）。读标签，不要只看正文：正文从不声明类型。**按需放大**：需要时抓取任何相关或已关闭工单的完整正文；调用 `## 说明` 里点名的技能。拿不准就调用两次：`grilling` 与 `domain-modeling`。
4. 记录落定：把答案作为**落定评论**发出，**关闭**该 issue，并在地图的“目前决策”里**追加一个上下文指针**。
5. 添加新浮出的工单（先建后连）；把答案已经明确化的迷雾毕业，并从**尚未明确**中清掉每一块毕业内容，让它只以新工单的形式存在。如果答案揭示某个工单（本工单或其他）在目的地之外，**判出范围**，而不是把它当作路线上的步骤解决。如果这个决策让地图的其他部分失效，更新或删除那些工单。

用户可能会并行跑未阻塞的工单，所以要预期其他会话正在同时编辑跟踪器。
