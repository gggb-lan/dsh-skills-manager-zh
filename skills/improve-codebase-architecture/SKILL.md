# 改进代码库架构

浮现架构摩擦并提出**加深机会**：把浅模块变成深模块的重构。目标是可测性与 AI 可导航性。

本命令受项目领域模型影响，并建立在共享设计词汇之上：

- 调用 `codebase-design` 技能获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、“接口就是测试面”、“一个适配器 = 假想接缝，两个 = 真实接缝”）。每个建议都严格使用这些术语，不要漂移到“组件”“服务”“API”“边界”。
- `GLOSSARY.md` 里的领域语言给好的接缝命名；`docs/adr/` 里的 ADR 记录着本命令不该重新争论的决策。

## 流程

### 1. 探索

**扫描之前先定范围：YAGNI。** 加深模块的价值在于让未来的改动更容易，所以要把额外权重放在最近变化过的代码上。看之前先决定**看哪里**：

- 用户点了方向（一个模块、子系统、痛点），就采用它，跳过下面的推断。
- 否则回看一段足够长的 commit 历史（`git log --oneline`），找出热点文件和区域，让这些路径先吸引你的注意力。如果改动很散、没有明显热点，就扩大范围。

先读项目词汇表（`GLOSSARY.md`）和你要触碰区域的 ADR。

然后起一个子代理走代码库。不要套死板启发式；有机地探索，记录你在哪里感到摩擦：

- 理解一个概念需要在许多小模块之间来回跳的地方？
- 模块**浅**、接口几乎和实现一样复杂的地方？
- 纯函数只是为了可测性被抽出来，而真正的 bug 藏在调用方式里（没有**局部性**）的地方？
- 紧耦合模块越过接缝泄漏的地方？
- 哪些部分没测试，或难以通过现有接口测试？

对你怀疑其浅的东西套用**删除测试**：删掉它是把复杂性集中起来，还是只是搬走？答案是“集中”，就是你要的信号。

### 2. 用 HTML 报告呈现候选

写一个自包含的 HTML 文件到系统临时目录，别让任何东西落进仓库。临时目录取 `$TMPDIR`，回退 `/tmp`（Windows 用 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，每次运行一个新文件。为用户打开它（Linux `xdg-open`、macOS `open`、Windows `start`），并给出绝对路径。

报告用 **CDN 上的 Tailwind** 做布局与样式，用 **CDN 上的 Mermaid** 画图，适用于关系是图状的地方。Mermaid 与手写 CSS/SVG 混用：关系是图状（调用图、依赖、时序）时用 Mermaid；想要更编辑化（质量图、剖面图、折叠动画）时用手写 div/SVG。每个候选都要有**前后可视化**。要有视觉。

每个候选渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么产生摩擦
- **方案**：用平实语言描述会改什么
- **收益**：用局部性和杠杆解释，以及测试会如何改善
- **前 / 后图**：并排、手绘，展示浅与深
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，做成徽章

报告最后加一节**首选推荐**：先做哪个候选，为什么。

**领域用 `GLOSSARY.md` 的词汇，架构用 `codebase-design` 的词汇。** 如果 `GLOSSARY.md` 定义了“Order”，就说“Order 接收模块”，不要说“FooBarHandler”，也不要说“Order 服务”。

**ADR 冲突**：如果候选与现有 ADR 矛盾，只有摩擦足够真实、值得重开 ADR 时才呈现。在卡片里明确标出（例如警告框：“与 ADR-0007 矛盾，但值得重开，因为……”）。不要列出 ADR 禁止的每一个理论重构。

完整 HTML 脚手架、图形模式与样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

**此时不要提接口。** 文件写完后问用户：“你想深入探讨哪一个？”

### 3. 追问循环

用户选定候选后，调用 `grilling` 技能，和他们一起走设计树：约束、依赖、加深后模块的形状、接缝后面放什么、哪些测试能活下来。

决策成型时副作用当场发生：调用 `domain-modeling` 技能，保持领域模型同步：

- **用了一个 `GLOSSARY.md` 里没有的概念给加深后的模块命名？** 把术语加进 `GLOSSARY.md`；文件不存在就按需创建。
- **讨论中磨锐了一个模糊术语？** 当场更新 `GLOSSARY.md`。
- **用户用有分量的理由否决了候选？** 提议写 ADR，措辞：“要不要我把它记成 ADR，让以后的架构审查不再重复建议它？”只有当未来探索者确实需要这个理由来避免重复建议时才提议；跳过临时理由（“现在不值得”）和不言自明的理由。
- **想探索加深后模块的替代接口？** 调用 `codebase-design` 技能，用它的 design-it-twice 并行子代理模式。
