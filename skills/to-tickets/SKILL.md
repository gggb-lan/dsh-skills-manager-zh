# 拆工单

把计划、规格或对话拆成一组**工单**：每个都是曳光弹式的垂直切片，并声明**阻塞**它的其他工单。

issue 跟踪器与分诊标签词汇应当已经提供给你。如果没有，提示用户先完成 `setup-matt-pocock-skills` 的配置。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容工作。如果用户传入了引用（规格路径、issue 编号或 URL），抓取它并读完整的正文与评论。

### 2. 探索代码库（可选）

如果还没探索过，先了解代码现状。工单标题与描述应使用项目领域词汇表的术语，并遵守正在改动区域的 ADR。

留意可以先行重构（prefactor）的机会，让实现更容易——“先把改动变简单，再做简单的改动”。

### 3. 起草垂直切片

把工作拆成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片要窄，但必须**完整**穿过每一层（schema、API、UI、测试）：是垂直的，不是某一层的水平切片
- 一个完成的切片必须能独立演示或验证
- 每个切片要能放进一个全新的上下文窗口
- 任何先行重构都应当先做

</vertical-slice-rules>

为每个工单标注**阻塞边**：必须先完成的其他工单。没有阻塞的工单可以立即开始。

**大范围重构是垂直切片的例外。** **大范围重构**指一次机械改动（重命名一列、给共享符号换类型），其**影响半径**横跨整个代码库，一次编辑会让成千上万个调用点同时失败，没有哪个垂直切片能保持绿灯。不要硬塞进曳光弹，按**扩展—收缩**排序：先扩展，把新形式与旧形式并存，确保不破坏任何东西；然后按影响半径分批迁移调用点（按包、按目录），每批一个工单并被“扩展”阻塞，因为旧形式还在，CI 可以逐批保持绿灯；最后收缩，在没有调用者后删除旧形式，其工单被所有迁移批次阻塞。如果连批次都无法单独保持绿灯，保留这个顺序，但让它们共享一个集成分支，并统一被最后的“集成与验证”工单阻塞——绿灯只在那里承诺。

### 4. 向用户确认

用编号列表展示拆分方案。每个工单显示：

- **标题**：简短描述性名称
- **被下列工单阻塞**：哪些工单必须先完成（若有）
- **交付内容**：该工单让什么端到端行为真正可用

问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确：每个工单是否只依赖真正卡住它的工单？
- 是否有工单需要合并或进一步拆分？

迭代直到用户认可。

### 5. 发布到配置好的跟踪器

发布已认可的工单。**怎么发**取决于 `setup-matt-pocock-skills` 配置的跟踪器；工单内容相同，只是阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每个工单一个文件，按依赖顺序从 `01` 编号（阻塞者在前）。每个文件的“被下列工单阻塞”列出它依赖的编号 / 标题。使用下面的单工单模板：一个文件一个工单，绝不要合成一个文件。
- **真实 issue 跟踪器（GitHub、Linear 等）** → 按依赖顺序每个工单发一个 issue（阻塞者在前），这样每条阻塞边都能引用真实标识。平台有原生阻塞关系就用原生关系，否则把“被下列工单阻塞”写成阻塞 issue 的引用。如果来源是已有 issue，把每个工单做成它的子 issue。除非另有指示，打上 `ready-for-agent` 标签。

按**前沿**推进：所有阻塞者都完成的工单即可开始。纯线性链就是从下往上。

不要关闭或修改任何父 issue。
