# 代码库设计

设计**深模块**：大量行为藏在一个小接口后面，放在干净的接缝上，并能通过该接口测试。凡是在设计或重构代码的地方，都用这套语言和这些原则。目标是给调用者**杠杆**，给维护者**局部性**，给所有人**可测性**。

## 词汇表

严格使用这些术语：不要替换成“组件”“服务”“API”“边界”。语言一致本身就是重点。

**模块（Module）**：任何有接口和实现的东西。刻意与尺度无关：一个函数、一个类、一个包，或一个横跨多层的切片。_避免_：单元、组件、服务。

**接口（Interface）**：调用者正确使用模块所必须知道的一切——类型签名，也包括不变量、顺序约束、错误模式、必需配置、性能特征。_避免_：API、签名（太窄，只指类型层表面）。

**实现（Implementation）**：模块内部的东西，它的代码主体。与**适配器（Adapter）**不同：一个东西可以是“实现很大的小适配器”（Postgres 仓库），也可以是“实现很小的大适配器”（内存假实现）。讨论接缝时用“适配器”，其余时候用“实现”。

**深度（Depth）**：接口处的杠杆。调用者（或测试）每学习一单位接口，能驱动多少行为。大量行为藏在**小**接口后面，模块就**深**；接口复杂程度几乎追上实现，模块就**浅**。

**接缝（Seam）**（Michael Feathers）：你可以在不编辑该处的情况下改变行为的地方；是模块接口所在的*位置*。接缝放在哪里是一个独立的设计决策，与接缝后面放什么不同。_避免_：边界（与 DDD 的限界上下文混淆）。

**适配器（Adapter）**：在接缝上满足某个接口的具体东西。描述的是*角色*（占哪个槽），不是实质（里面是什么）。

**杠杆（Leverage）**：调用者从深度中得到的东西。每学一单位接口，获得更多能力。一份实现回馈给 N 个调用点、M 个测试。

**局部性（Locality）**：维护者从深度中得到的东西。改动、缺陷、知识与验证集中在一处，而不是散到调用者那里。修一次，处处修好。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│      小接口          │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│      深实现          │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（要避免）：

```
┌─────────────────────────────────┐
│           大接口                 │  ← 方法多，参数复杂
├─────────────────────────────────┤
│      薄实现                      │  ← 只是转发
└─────────────────────────────────┘
```

设计接口时问自己：

- 能不能减少方法数量？
- 能不能简化参数？
- 能不能把更多复杂度藏进去？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小的、可 mock、可替换的部件组成；它们只是不属于接口。模块可以同时有**内部接缝**（实现私有，供自己的测试使用）和接口处的**外部接缝**。
- **删除测试。** 想象删掉这个模块：复杂性消失了，说明它只是个转发；复杂性在 N 个调用者那里重新冒出来，说明它确实在创造价值。
- **接口就是测试面。** 调用者和测试跨过同一个接缝。如果你想**绕过**接口去测试，说明模块形状多半不对。
- **一个适配器意味着假想的接缝，两个适配器意味着真实的接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测性设计

好接口让测试变得自然：

1. **接受依赖，不要自己创建。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积要小。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用者与测试的表面）。
- **深度**是**模块**相对其**接口**衡量的属性。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**坐在**接缝**上并满足**接口**。
- **深度**为调用者产生**杠杆**，为维护者产生**局部性**。

## 被否定的表述

- **深度 = 实现行数 / 接口行数**（Ousterhout）：这会奖励把实现写长。我们改用“深度即杠杆”。
- **“接口” = TypeScript 的 `interface` 关键字或类的公共方法**：太窄；这里的接口包含调用者必须知道的一切事实。
- **“边界”**：与 DDD 的限界上下文混淆。请说**接缝**或**接口**。
