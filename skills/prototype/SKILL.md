# 原型

原型是**用来回答问题的废弃代码**。问题决定形状。

## 选择分支

用用户的提示、周边代码，或直接问用户（如果人在）来判断正在回答哪个问题：

- **“这段逻辑 / 状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。做一个单独可分享的 HTML 文件（自由操作按钮 + 分标签的引导式走查），把状态机推进到纸面上很难推理的情形，并让非开发者也能操作。
- **“它该长什么样？”** → [UI.md](UI.md)。在同一路由上生成几种**截然不同**的 UI 变体，用 URL 查询参数和底部浮动栏切换。

两个分支产出的东西差别极大，选错等于整个原型白做。如果问题确实模糊且联系不到用户，就选与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两个分支都适用的规则

1. **从第一天就标明是一次性的，且写得清清楚楚。** 原型代码要放在它将来实际使用的位置附近（模块或页面旁边），让上下文显而易见；但命名要让随手看到的人知道这是原型，不是生产代码。一次性 UI 路由要遵守项目既有的路由约定，不要另起一套顶层结构。
2. **启动要极其简单。** UI 原型从项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击就能打开的单个 HTML 文件。总之，启动不需要动脑。
3. **默认不做持久化。** 状态放在内存里。持久化是原型要**检验**的东西，不是它该依赖的东西。如果问题明确涉及数据库，用一个临时库或命名清楚（“PROTOTYPE，用完删我”）的本地文件。
4. **跳过打磨。** 不写测试，除了让原型**能跑**之外不做错误处理，不做抽象。重点是快速学到东西。
5. **暴露状态。** 每次操作后（逻辑）或每次切换变体后（UI），打印或渲染完整相关状态，让用户看到变化。
6. **结束时把它留住。** 把验证过的决策并回真实代码，然后把原型本身作为**一手来源**留存：提交到一个一次性分支、离开 main，并在实现 issue 上留下指向该分支的上下文指针。同时把答案（结论以及它解决了什么问题）记进 issue 或 commit。main 只保留被验证的决策。
