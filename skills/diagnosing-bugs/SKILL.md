# 诊断 Bug

针对难缠 bug 的纪律。只有明确给出理由时才跳过阶段。

探索代码库时，读 `GLOSSARY.md`（如果存在）以建立相关模块的清晰心智模型，并查看你正在改动区域的 ADR。

## 脱敏

本技能会要求你展示命令、输出与抓取物。**先对所有秘密脱敏**：用 `<REDACTED>` 代替。用环境变量构建回路，让凭据留在环境里而不是出现在你展示的内容里。抓取物里带着认证头：只引用承载信号的那几行。

如果脱敏后的输出不足以诊断，直接说明，并去问用户。

## 阶段 1：建立反馈回路

**这就是本技能的核心。** 其余都是机械动作。如果你有一个**紧**的通过/失败信号（在**这个** bug 上会变红），你就能找到原因；二分、假设检验、插桩都只是在消费它。没有它，盯着代码看多久都救不了你。

在这里花不成比例的努力。**要激进。要有创造力。拒绝放弃。**

### 构造回路的方式，大致按这个顺序

1. **失败的测试**，落在任何能触达该 bug 的接缝上：单元、集成、端到端。
2. **curl / HTTP 脚本**，打向运行中的开发服务器。
3. **CLI 调用**，带固定输入，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/控制台/网络做断言。
5. **回放抓取到的 trace**：把真实的网络请求 / payload / 事件日志存到磁盘，隔离地回放进代码路径。
6. **一次性测试台**：起系统的最小真子集（一个服务、mock 依赖），用一次函数调用跑通 bug 所在的代码路径。
7. **属性 / 模糊测试循环**：如果 bug 是“偶尔输出错误”，跑 1000 个随机输入找失败模式。
8. **二分测试台**：如果 bug 出现在两个已知状态之间（commit、数据集、版本），把“在状态 X 启动、检查、重复”自动化，以便 `git bisect run`。
9. **差分回路**：同一输入分别跑旧版本 vs 新版本（或两套配置），diff 输出。
10. **HITL bash 脚本**：最后手段。如果必须有人点击，就用 `scripts/hitl-loop.template.sh` 去驱动**他**，让回路保持结构化。抓取到的输出再回传给你。

建立对的反馈回路，bug 就修好了 90%。

### 收紧回路

把回路当成一个产品。一旦**有了**回路，就**收紧**它：

- 能不能更快？（缓存准备步骤、跳过无关初始化、缩小测试范围。）
- 信号能不能更锐？（断言具体症状，而不是“没崩”。）
- 能不能更确定？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

30 秒的偶发回路几乎不比没有回路强；2 秒的确定性回路才叫紧，那是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发循环 100 次、并行、加压、缩小时间窗口、注入 sleep。50% 偶发的 bug 可调，1% 不可调，所以持续提高复现率直到可调。

### 确实建不出回路时

停下来，明确说出来。列出你试过什么。向用户要：(a) 能复现问题的环境访问权；(b) 脱敏后的抓取物（HAR 文件、日志转储、core dump、带时间戳的录屏）；或 (c) 允许添加临时生产插桩。**没有回路就不要进入假设阶段。**

### 完成判据：一条会变红的紧回路

阶段 1 完成的标志是回路既**紧**又**能变红**：你能说出**一条命令**（脚本路径、测试调用、curl），并且你**已经至少跑过一次**（展示调用与输出，脱敏），且它满足：

- [ ] **能变红**：它驱动真实的 bug 代码路径，并断言**用户的确切症状**，所以能在这个 bug 上变红、修好后变绿。不是“跑起来不报错”；它必须能**抓住这个具体 bug**。
- [ ] **确定性**：每次运行结论一致（偶发 bug 则按上面的方式固定并提高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **代理可跑**：你能无人值守地运行；需要人时只通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在这条命令存在之前就开始读代码建理论，**停下：直接跳到假设正是本技能要防的失败模式。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路。看着它随着 bug 出现而变红。

确认：

- [ ] 回路复现的是**用户**描述的失败模式，而不是碰巧附近的另一种失败。搞错 bug = 搞错修复。
- [ ] 失败在多次运行中可复现（非确定性 bug 则复现率足够高、足以调试）。
- [ ] 你已经捕获确切症状（错误信息、错误输出、慢的耗时），让后续阶段能验证修复确实针对它。

### 最小化

一旦变红，就把复现缩到**仍然变红的最小场景**。**一次一个**地砍掉输入、调用者、配置、数据、步骤，每砍一次重跑回路，只保留对失败有承重作用的元素。

为什么要这么做：最小复现能缩小阶段 3 的假设空间（剩下可怀疑的活动部件更少），并在阶段 5 变成干净的回归测试。

完成判据：**剩下的每个元素都承重**——去掉任何一个，回路就变绿。

在**复现并最小化**之前不要继续。

## 阶段 3：提出假设

在测试任何一个之前，先产生 **3–5 个排好序的假设**。只生成一个会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。”

如果你说不出预测，这个假设只是感觉：丢掉或磨锐它。

**测试之前把排序列表给用户看。** 他们常有领域知识能瞬间重排（“我们刚给 #3 部署了改动”），或者已经排除过某些假设。这是个便宜的检查点，能省大量时间。不要因此阻塞；用户不在时就按你的排序继续。

## 阶段 4：插桩

每个探针都必须对应阶段 3 中某个具体预测。**一次只改一个变量。**

工具优先级：

1. 环境支持就用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界上打**定向日志**。
3. 绝不要“全量打日志然后 grep”。

**给每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾时就变成一次 grep。没打标签的日志会活下来；打了标签的会死掉。

**性能分支。** 性能回归通常不该用日志。改为：先建立基线测量（计时脚手架、`performance.now()`、profiler、查询计划），再二分。先测量，再修。

## 阶段 5：修复 + 回归测试

在修复**之前**写回归测试，但前提是存在**正确的接缝**。

正确的接缝，指测试能在调用点复现**真实的 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用者，却只能写单调用者测试；单元测试复现不了触发 bug 的链路），在那里写回归测试只会带来虚假的安心。

**如果没有正确的接缝，这本身就是一条发现。** 记下来。代码库架构正在阻止这个 bug 被锁死。把它标记给下一阶段。

如果有正确的接缝：

1. 把最小复现变成该接缝上的失败测试。
2. 看着它失败。如果你是通过改代码或 fixture 强制变红的，先与干净副本 `diff`，证明改动确实生效，再相信它。
3. 应用修复。
4. 看着它通过。
5. 对**原始的（未最小化的）**场景重跑阶段 1 的反馈回路。

## 阶段 6：收尾

宣布完成前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或已记录接缝缺失）
- [ ] 所有 `[DEBUG-...]` 插桩都已移除（grep 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 最终正确的假设写进 commit / PR 信息，让下一个调试者也能学到
