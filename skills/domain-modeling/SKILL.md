# 领域建模

在设计过程中主动建立并打磨项目的领域模型。这是**主动**的纪律：质疑术语、虚构边界场景、并在它们成型的当下把词汇表与决策写下来。（仅仅为了取词而**读** `GLOSSARY.md` 不算本技能：那是任何技能都能做的一行习惯。本技能用于你**改变**模型，而不只是消费它。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明仓库有多个上下文。地图指向每个上下文的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

**按需创建文件**：只有确实有东西要写时才建。没有 `GLOSSARY.md` 就等第一个术语确定时再建；没有 `docs/adr/` 就等第一条 ADR 需要时再建。

## 会话过程中

### 拿词汇表对质

当用户使用的术语与 `GLOSSARY.md` 中既有语言冲突时，立刻指出。“你的词汇表把‘取消’定义为 X，但你似乎指的是 Y。到底是哪个？”

### 磨锐模糊语言

当用户使用含糊或超载的术语时，提出一个精确的规范术语。“你说的‘账号’是指 Customer 还是 User？这是两个不同的东西。”

### 讨论具体场景

讨论领域关系时，用具体场景压力测试。虚构能探到边界的情况，逼用户把概念之间的界线说清楚。

### 与代码交叉验证

用户陈述某事如何工作时，检查代码是否同意。发现矛盾就摆出来：“你的代码取消的是整个 Order，但你刚说可以部分取消。哪个是对的？”

### 当场更新 GLOSSARY.md

一个术语确定时，立刻更新 `GLOSSARY.md`。不要攒批：随发生随记录。格式见 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 应当**完全不包含**实现细节。不要把它当规格、草稿本或实现决策的仓库。它就是一份词汇表，仅此而已。

### 谨慎提议 ADR

只有以下三条**同时成立**时才提议写 ADR：

1. **难以回退**：以后改变主意的代价是实质性的
2. **脱离上下文会意外**：未来的读者会想“他们为什么这么做？”
3. **真实权衡的结果**：确实存在其他选项，而你出于具体理由选了这一个

三条缺一，就跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
