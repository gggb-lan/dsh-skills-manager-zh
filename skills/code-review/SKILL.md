对 `HEAD` 与用户给定固定点之间的 diff 做双轴审查：

- **规范**：代码是否符合本仓库文档化的编码规范？
- **规格**：代码是否忠实实现了来源 issue / 规格？

两条轴用**并行的子代理**跑，避免互相污染上下文，然后由本技能汇总。

issue 跟踪器应当已经提供给你。如果没有，提示用户先运行 `setup-matt-pocock-skills`。

## 流程

### 1. 固定基准点

用户说的就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。没指定就问。

固定只捕获一次 diff 命令：`git diff <fixed-point>...HEAD`（三点，等价于与 merge-base 比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

继续之前先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。坏引用或空 diff 应该在这里失败，而不是在两个并行子代理里才失败。

### 2. 定位规格来源

按以下顺序寻找来源规格：

1. commit 信息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），按跟踪器文档里的方式抓取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 都找不到就问用户规格在哪里。如果用户说没有，**规格**子代理跳过并汇报“无规格可用”。

### 3. 定位规范来源

搜索仓库里所有记录“代码该怎么写”的文件。存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 时必须纳入。

在仓库文档之外，规范轴始终携带下面的**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也适用。两条约束：

- **仓库优先。** 文档化的仓库规范永远胜出；它支持的东西即使基线会标记，也要抑制。
- **始终是判断题。** 每条坏味道都是有标签的启发式（“可能是 Feature Envy”），绝不是硬性违规。像这里所有规范一样，工具已经强制的内容跳过。

每条坏味道按“是什么 → 怎么修”读，并对照 diff 匹配：

- **神秘命名**：函数、变量或类型的名字看不出它做什么 / 存什么。→ 重命名；如果找不到诚实的名字，说明设计本身含糊。
- **重复代码**：同一种逻辑形状在本次改动的多个 hunk 或文件中出现。→ 抽出共享形状，两处都调用它。
- **依恋情结**：某个方法访问另一个对象的数据比访问自己的还多。→ 把方法移到它依恋的数据上。
- **数据泥团**：同几个字段或参数总是结伴出现（一个想诞生的类型）。→ 把它们打包成一个类型传过去。
- **基本类型偏执**：用基本类型或字符串代替一个值得拥有独立类型的领域概念。→ 给这个概念一个小的专属类型。
- **重复的 switch**：对同一类型的同一个 `switch`/`if` 级联在改动中反复出现。→ 换成多态，或两处共享一张映射表。
- **霰弹式修改**：一个逻辑改动迫使 diff 里许多文件零散修改。→ 把总是一起变化的东西聚到一个模块。
- **发散式变化**：同一个文件或模块因为几个不相关的原因被反复修改。→ 拆分，让每个模块只因一个原因变化。
- **夸夸其谈通用性**：为规格没有的需求添加抽象、参数或钩子。→ 删掉；内联回去，直到出现真实需求。
- **过长的消息链**：调用方不该依赖的长链 `a.b().c().d()` 导航。→ 在第一个对象上用单个方法把这段走查藏起来。
- **中间人**：一个类或函数基本只是转发。→ 去掉它，直接调用真正的目标。
- **被拒绝的遗赠**：子类或实现者忽略 / 覆盖了继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

两个子代理调用一起发出、在前台运行，然后汇总它们返回的报告。

**规范子代理提示词**应包含：

- 完整的 diff 命令与 commit 列表。
- 你在第 3 步找到的规范来源文件清单，**外加第 3 步的坏味道基线全文**（子代理没有别的途径拿到它）。
- 任务说明：“逐文件 / hunk 汇报：(a) diff 违反文档化规范的每一处，引用规范（文件 + 规则）；(b) 你发现的基线坏味道，说出名字并引用该 hunk。区分硬性违规与判断题：违反文档化规范可以是硬性的，基线坏味道永远是判断题，且仓库文档优先于基线。工具已强制的内容跳过。400 词（约 600 汉字）以内。”

**规格子代理提示词**应包含：

- diff 命令与 commit 列表。
- 规格的路径或抓取到的内容。
- 任务说明：“汇报：(a) 规格要求但缺失或只做了一半的需求；(b) diff 中没被要求的额外行为（范围蔓延）；(c) 看起来实现了但实现方式可疑的需求。每条结论引用对应规格原文。400 词（约 600 汉字）以内。”

如果规格缺失，跳过规格子代理，并在最终报告中说明。

### 5. 汇总

把两份报告分别放在 `## 规范` 与 `## 规格` 标题下，原文或轻度清理后呈现。**不要**合并或重新排序，因为两条轴是刻意分开的（见“为什么要两条轴”）。

最后用一行总结：每条轴的发现总数，以及**各轴内部**最严重的问题（如果有）。不要跨轴选唯一赢家——那正是分离两轴要防止的重新排序。

## 为什么要两条轴

一个改动可以通过一条轴而失败另一条：

- 遵守所有规范但实现了错误的东西 → **规范通过，规格失败**
- 完全按 issue 实现但破坏项目约定 → **规格通过，规范失败**

分开汇报才能防止一条轴掩盖另一条。
