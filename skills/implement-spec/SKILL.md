你已经拿到一份规格。它应当有关联的工单，描述如何实现这份规格。

issue 跟踪器应当已经提供给你。如果没有，提示用户运行 `setup-matt-pocock-skills`。

目标是在**一个集成分支**上实现整份规格，每个工单都按 issue 跟踪器关闭工作的方式解决。

工单不是步骤清单，而是一张带阻塞关系的**任务图**。这意味着总有一个**前沿**，上面的工单随时可拿。

与子代理之间的通信应当稀疏。主要通过**上下文指针**沟通：指向规格、工单、研究笔记、之前的 commit。不要重复指针已经能拿到的信息。

**实现子代理**尽可能在后台跑，以获得最大并发。

## 步骤

1. 读规格与工单，理解任务图。

2. （可选）用**探索子代理**完成工单所需的探索——相关代码文件或外部文档。确保探索子代理能写文件：把它的 Markdown 笔记存到仓库外一个所有后续子代理都能访问的目录。这样**实现子代理**可以专注实现而不是探索。

3. 创建集成分支。如果跟踪器通过 PR 关闭工作，或用户要求，就在第 5 步第一次合并后开一个 draft PR（领先 main 零 commit 的分支开不了 PR），标明会关闭规格与工单。

4. 用**实现子代理**实现每个工单，每个子代理在自己的 worktree 和自己的分支上。每个实现子代理：
   - 开始前确认自己的 worktree 基于集成分支，否则 reset 到它；
   - 调用 `tdd` 技能构建该工单；
   - 汇报完成前把集成分支最新提交合并进自己的分支。

5. 一个**实现子代理**完成后，用一个**合并子代理**把它的工作合并进集成分支。

6. 如果这让可用工单的**前沿**发生变化，再启动更多**实现子代理**处理新工单。这能让并发最大化。

7. 全部工单完成后，在集成分支上调用 `code-review` 技能。让一个**实现子代理**统一修掉所有问题。

8. 如果存在 draft PR，标记为可审查。否则按跟踪器的方式逐个解决工单，并汇报集成分支。

9. 清理所有**实现子代理**的 worktree。
