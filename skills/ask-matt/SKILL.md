# Ask Matt

你记不住每个技能，所以来问。

在说明某个技能做什么、或建议跳过某一步之前，先读那个技能的 SKILL.md：这里的摘要只用于定位。

**流程**（flow）是穿过技能的一条路径。多数路径沿一条**主流程**走，两个**入口**并入它。其余是独立技能，或在底下运行的词汇层。

## 主流程：想法 → 交付

多数工作走的路线。你有一个想法，想把它做出来。

1. **`grill-with-docs`** 用访谈把想法磨锐。只要你在**工作目录**里，就从这里开始：它是有状态的，会把学到的东西留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？用 `grill-me`，见“独立技能”。两者跑同一个 `grilling` 原语；`grill-with-docs` 会留下纸面记录，所以只要仓库在那儿，它就是更好的那个。）
2. **分支：所有问题都能在对话里定下来吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看到的 UI），就绕道原型，两个方向都用 **`handoff`** 衔接（原型在自己的目录里，正是 `handoff` 的用途）：
   - **`handoff`** 出去，开一个新会话针对那份文件，
   - **`prototype`** 用一次性代码回答问题，
   - 再 **`handoff`** 回来，并从最初的想法线程引用它。
3. **分支：这是多会话的构建吗？**
   - **是** → **`to-spec`**（把线程变成规格），再 **`to-tickets`** 拆成曳光弹工单，每个都声明**阻塞边**。然后两种方式之一推进：
     - 每个工单跑一次 **`implement`**，两次之间 **`clear`** 上下文。本地跟踪器上就是 `.scratch/<feature>/issues/` 下一工单一个文件，按阻塞优先手工推进；真实跟踪器上阻塞边是原生链接，任何阻塞者已完成的工单都能被拿。
     - **`implement-spec`** 一次跑完整份规格。它把工单当作**任务图**，在就绪**前沿**上并行跑实现子代理，全部落到一个**集成分支**。
   - **否** → 就在当前上下文里跑 **`implement`**。

   无论哪种，代码都由 **`tdd`** 驱动（一次一个红-绿切片），最后以 **`code-review`** 收尾（规范 + 规格双轴审查 diff）。`implement` 每个工单跑一次两轴；`implement-spec` 的每个实现者各自跑 `tdd`，最后对集成分支跑一次 `code-review`。只想不用完整规格、测试先行地做一个具体行为时，单独用 `tdd`；只想对照固定点审查分支或 PR 时，单独用 `code-review`。

   工作以 PR 形式提交时，**`pr`** 塑造正文：最小的可视化、前后证据、单向门还是双向门。

4. **`retro`** 闭环。构建之后，尤其是跑偏之后，它回看会话并建议改**环境**而不是代码：导航指针、自动检查、`code-review` 执行的编码规范、指导文件、工具。机械性错误变成确定性检查，判断题变成编码规范。

### 上下文卫生

步骤 1–3 保持在**一个不中断的上下文窗口**里（在 `to-tickets` 之前不要 compact 或 clear），让追问、规格、工单建立在同一套思考上。之后每次 `implement` 都是全新的，从工单出发。`retro` 要在它回看的那次会话里跑；清理之后就指向那次会话的日志。

限制是**[智能区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能锐利推理的窗口（当前模型约 150k token）。如果还没到 `to-tickets` 就逼近上限，不要在退化状态下硬撑；在最近的阶段边界 `compact` 后继续。

## 入口

一种会产生工作、然后并入主流程的起始处境。

- **bug 和需求堆积** → **`triage`**。它把 issue 推过各个分诊角色，产出 agent-ready 的 issue，之后由 `implement` 接手。

  分诊只用于**不是你创建**的 issue：bug 报告、外来功能请求、任何原始到达的东西。`to-tickets` 产出的工单已经 agent-ready，**不要**再分诊。

- **有东西坏了** → **`diagnosing-bugs`**。用于难缠的：一眼看不出的、间歇的、在两个已知正常状态之间潜入的回归。它拒绝在拿到**紧的反馈回路**（一条已经在这个 bug 上变红的命令）之前进入理论，然后用回归测试修复。修完之后在同一会话跑 `retro`，问“什么本可以防止它”；如果真正的发现是没有好接缝能锁住它，那是 `improve-codebase-architecture` 的活。

- **巨大而模糊的工作：绿地项目或超出单会话的大功能** → **`wayfinder`**，这里认知负担最重的流程。当通往目的地的路还看不见时，它在 issue 跟踪器上画一张**共享地图**和一组**决策工单**，逐个解决，产出**决策而不是交付物**，直到迷雾退去。`grill-with-docs` 磨锐一个你能在一个会话里握住的想法；wayfinder 用于你握不住的那个。它更慢更密，只留给这种情况，绝不要用于范围清楚的功能。

  地图清晰后，**它交接，不构建**：在 `to-spec` 处并入主流程，把地图里链接起来的决策收敛成可构建的计划，然后照常 `to-tickets` 和 `implement`。把地图直接接进 `implement` 会跳过这次收敛，把链接的细节丢掉；只有发现这次工作其实很小，才直接 `implement`。

## 代码库健康

不是功能工作，只是维护。

- **`improve-codebase-architecture`** 在你有点空闲时跑，让代码库保持适合代理运作。它浮现**加深机会**；选一个就**生成一个想法**，可以带进主流程的 `grill-with-docs`。它是找候选的普查；`codebase-design` 是设计所选方案的基准台。

## 底下的词汇层

两篇模型调用的参考，运行在其他技能**底下**，各自是其词汇的单一事实源。当问题在**词**而不在流程时直接用它们，或让上面的技能把它们拉进来。

- **`domain-modeling`**：磨锐项目的**领域**语言：质疑模糊术语、拆解超载词（“账号”同时干三件事）、把难以回退的决策记成 ADR。它是 `grill-with-docs` 驱动的主动纪律，用来让 `GLOSSARY.md` 保持干净。
- **`codebase-design`** 是深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的**形状**：大量行为藏在小接口后、放在干净接缝上。`tdd` 和 `improve-codebase-architecture` 都说这套语言。

## 阶段边界

**阶段**是会话内的一块工作：追问、实现、QA。两个阶段之间的**边界**上有五个选项，选哪个是整张地图里最模糊的决定：

- **继续**：原地不动。不花成本，不丢东西。
- **`clear`**：清空窗口，当这里的东西对下一步都不重要时。
- **`handoff`** 写一份可携带的 Markdown。范围窄：只用于**新 harness**、**新目录**、**同事**，或阶段中途分叉一个侧任务。它买的是可携带性。
- **子代理**：把范围紧的任务发到它自己的窗口，拿回报告。
- **`compact`** 压缩当前上下文并用它启动新会话。这是**默认**，在决策树的底部，而不是第一选择。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看有序决策树：五个问题、每个分支的理由，以及为什么“一手来源的成本”让**继续**成为最该先排除的选项。在边界上做决定；阶段中途，继续，或把剩下的拆给子代理。

## 独立技能

完全在主流程之外。

- **`grill-me`**：和 `grill-with-docs` 一样的持续访谈，但**无状态**：不在本地保存，也不建 `GLOSSARY.md`。当你不**在**工作目录里时用它（磨锐计划、设计、一篇文字，任何底下没有仓库的东西）。如果在工作目录里，用 `grill-with-docs`：同样的访谈，还留下纸面记录，严格更优。
- **`grilling`** 是访谈原语本身：轮次、前沿、事实归代理、决策归你。`grill-me` 与 `grill-with-docs` 是两个具名入口，`triage`、`wayfinder`、`improve-codebase-architecture` 内部都会跑它。只有想要不带包装的访谈时，才直接用它。
- **`prototype`** 是一个小而一次性的程序，回答一个设计问题：这个状态模型对不对，或这个 UI 该长什么样。一次性是对代码写法的约束，不是销毁它的承诺：答案并回真实代码，原型本身留在一个从 main 分出的 `prototype/<name>` 分支上作为**一手来源**，由实现 issue 指向它。
- **`research`**：把阅读工作交给**后台代理**：它针对**一手来源**调查，然后在仓库里留下带引用的 Markdown 文件。它阅读时你可以继续工作。
- **`to-questionnaire`**：卡住你的东西不在你脑子里、也不在代码库里，而在**别人**那里时用它，它替你写一份问卷让对方填。它是 `grill-me` 的反面：不访谈你关于主题，而是访谈你关于**这次发送**（给谁、要拿回什么），再把问题对准缺口。
- **`wizard`** 用于只有**人**能做的步骤：开通基础设施、配置凭据或 CI secret、走陌生的第三方控制台、跑一次性的迁移或切换。它生成一个交互式 bash 脚本，逐项打开 URL、捕获每个值、写进 `.env` 和 GitHub secrets，让这套流程不再需要每次向代理重新解释。
- **`wait-what`** 是“消息没落地”时的矫正。在任何其他技能里、对话中途都能用，代理会用你缺的上下文、平实的语言、`GLOSSARY.md` 的词汇把刚才的话重讲一遍。
- **`teach`**：跨多个会话学习一个概念，用当前目录作为有状态的学习工作区。
- **`writing-for-agents`** 是写“给代理看的文档”的参考：技能、AGENTS.md、被指针指向的文档。
