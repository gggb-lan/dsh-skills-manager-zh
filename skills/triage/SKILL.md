# 分诊

让项目 issue 跟踪器上的 issue 走一个小的分诊角色状态机。

如果本仓库把外部 PR 当作请求入口（见 issue-tracker 配置），分诊也覆盖它们：**PR 就是附带代码的 issue**，使用同样的角色、状态与机器，只有下面标了“对 PR”的几处差异。裸 `#42` 按跟踪器配置解析成 issue 或 PR。

分诊期间发到跟踪器的每条评论或 issue，**必须**以下面的免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：怎么写可长期使用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库怎么运作

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已完整说明，可由 AFK 代理接手
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对 PR，同样的状态读作针对附带代码：`ready-for-agent` 表示已附简报、代理应在 diff 上走下一步；`ready-for-human` 表示可以交给人合并。

每个已分诊的 issue 应恰好带一个类别角色和一个状态角色。状态角色冲突时先标记出来，做任何事之前问维护者。

这些是标准角色名。跟踪器里实际的标签字符串可能不同，映射应已提供给你。如果没有，提示用户运行 `setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先到 `needs-triage`；从那里可去 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后 `needs-info` 回到 `needs-triage`。维护者可随时覆盖；看起来不寻常的流转先标记并询问。

## 调用

维护者调用 `triage` 并用自然语言说明想要什么。解释请求并执行。例如：

- “给我看需要我处理的东西”
- “看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有什么 agent 可以接的？”

## 展示需要关注的内容

查询跟踪器，按最旧优先呈现三类：

1. **未打标签**：从未分诊。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且上次分诊笔记之后报告者有活动**：需要重新评估。

PR 在范围内时，把外部 PR 也放进这些桶，并在每行标 `[PR]` 或 `[issue]`。发现阶段只呈现**外部** PR（跟踪器配置定义谁算外部），协作者正在进行的 PR 不算分诊工作。这个过滤只用于发现；明确点名的 PR 无论作者是谁都要分诊。

显示数量与每项一行摘要，让维护者挑。

## 分诊某个具体 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析之前的分诊笔记，别重复问已解决的问题。用项目领域词汇表探索代码库，遵守相关 ADR。对代码库做两项检查：(a) **冗余**：按领域概念（不只是请求的措辞）搜索是否已有该行为的实现，并汇报你查过哪里。找到了，就是已实现的 `wontfix`（第 5 步）。(b) **此前被拒**：读 `.out-of-scope/*.md`，列出任何相似的请求。

2. **给建议。** 告诉维护者你的类别与状态建议及理由，附上与该请求相关的代码库摘要（包括是否已实现）。等待指示。

3. **验证主张。** 任何追问之前，先确认主张站得住。bug 就按报告者的步骤复现；PR 就确认 diff 确实做了它声称的事：checkout、跑相关测试或命令。汇报结果：已确认（带代码路径）、失败、或细节不足（强 `needs-info` 信号）。已确认的验证能让 agent 简报强得多。

4. **追问（如需要）。** 请求需要充实，就调用两次技能：`grilling` 与 `domain-modeling`，一轮一轮问成形，磨锐领域术语，并随决策落定当场更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但说明为什么不能委派（判断类决策、外部访问、设计决策、手工测试）。
   - `needs-info`：发分诊笔记（模板见下）。
   - `wontfix`：关闭 issue，评论取决于**为什么**：
     - **已实现**：代码库里已存在该改动。指出位置；**不要**写进 `.out-of-scope/`（那个知识库用于**被拒**的请求，不是已建成的）。
     - **拒绝（bug）**：礼貌解释，然后关闭。
     - **拒绝（enhancement）**：写进 `.out-of-scope/`，从评论链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用角色。有部分进展时可留可选评论。

## 快速覆盖状态

维护者说“把 #42 移到 ready-for-agent”，就信任他，直接应用角色。确认你将要做什么（角色变更、评论、关闭），然后执行。跳过追问。如果没经过追问就移到 `ready-for-agent`，问他们要不要写 agent 简报。

## needs-info 模板

```markdown
## 分诊笔记

**目前已经确认的：**

- 要点 1
- 要点 2

**还需要你（@报告者）提供：**

- 问题 1
- 问题 2
```

把追问中解决的一切都记进“已经确认”，别让工作丢失。问题必须具体可执行，不能是“请提供更多信息”。

## 恢复此前的分诊

如果 issue 或 PR 上已有分诊笔记，读它们，检查报告者是否回答了未决问题，在继续前呈现更新后的全貌。不要重复问已解决的问题。
