用户要求做一次**复盘**。你是在为编码代理的**环境**提出改进建议，以提升后续运行质量。

## 步骤

1. 调用 `writing-for-agents` 技能获取写作风格指南。

2. 读用户指定的那次会话的一手材料。这可能意味着在本机搜索会话日志。用户没指定就默认当前会话。

3. 在以下类别中寻找改进候选。

- **导航**：代理找对文件有多容易？文件之间有没有隐藏依赖？加一个**导航指针**会不会更容易？*何时使用*：会话花了很长时间才找到某条信息。
- **自动化检查**：有没有能抓住代理所犯错误的自动检查？lint、类型检查、测试、文件系统 lint？先读仓库自己的检查命令（`package.json` / 构建工具里的 `lint`/`check` 脚本、CI 流程），这样“已经存在但没接上或悄悄坏掉”的检查本身就是发现，而不是重新发明。没有**护栏**（没有 pre-commit hook，也没有跑 lint/类型检查/测试的 CI 任务）的仓库本身就是一条发现：没接 lint 的仓库是持续的错失，而不是中性默认。*何时使用*：代理犯了本可被自动检查抓住的错误，或仓库完全没有护栏。
- **编码规范**：是否该给**审查代理**一条新规则去执行？是否该删除或澄清已有规则？先给违规分类：**机械性**的（固定语法模式、禁用 API、import 形状、文件位置规则）一律做成确定性检查——仓库 linter 里的自定义规则、新的 pre-commit hook、或新的 CI 任务，哪个成本最低用哪个。默认做检查而不是写规则。`CODING_STANDARDS.md` 只留给真正的**判断题**（跨文件一致性、“与周边风格一致”、任何护栏无法替代的东西）。*何时使用*：审查代理漏掉了某个错误。
- **全局 AGENTS.md**：有没有指导性指令应该移到编码规范（或自动检查）里？*何时使用*：AGENTS.md 特别大——无论是仓库里还是用户的全局作用域。
- **工具经济性**：代理有没有做昂贵的工具调用本可精简？有没有自定义工具（CLI、MCP）特别耗 token？*何时使用*：代理做了昂贵的工具调用。
- **空操作**：在指导文件里有没有不改变代理行为的指令。*何时使用*：指导文件又大又难维护。
- **信息获取**：有没有机会增加代理可获取的信息？把开发服务器日志 tee 出来、给第三方服务的只读访问。*何时使用*：某个关键信息代理拿不到。

4. 按严重程度从高到低把这些候选呈现给用户。

## 参考

### 实现 vs 审查

记住所有工作都经过两个阶段：实现与审查。实现代理的**上下文压力**最大——它负责探索、写代码、调 bug。

审查代理的上下文压力最小——它拿到的是 diff，不需要探索，通常也不需要写代码或调试。

这意味着编码规范应该由审查代理来施加，而不是实现代理。

### 文件

你可以动用仓库里的几类文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推入任何在此仓库工作的代理上下文，应极其克制地使用，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：在审查时读，实现时不读。如果标准文件超过 1000 行，加导航指针指向 docs 目录。
- 文档：把文档当参考文件，由其他文件指过来。写新文档前先找已有文档。
- 技能：把文档（因为其 description 会进入代理上下文）或用户调用的命令做成技能。遵循 `writing-for-agents` 技能里的建议。
