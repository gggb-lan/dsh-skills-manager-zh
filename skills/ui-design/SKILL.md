# UI 设计与验收

核心原则：**先定规范，再写页面**。AI 直接写页面最常见的失败不是“代码跑不起来”，而是“结构对、气质错”——颜色、间距、层级、状态各写各的，最后不是你想要的东西。本技能把 UI 变成一份可验证的契约。

## 何时使用

- 新建页面、改版、新增组件
- 用户说“做个界面 / 页面 / 后台 / 仪表盘”
- 原型阶段需要多套方案对比
- code review 涉及界面改动

## 流程（四阶段，逐阶段确认）

### 1. 需求澄清

与 `grilling` 配合，先问清楚：

- 目标用户与使用场景
- 信息优先级（第一眼必须看到什么）
- 参考物（截图、竞品、品牌规范）
- 技术约束（框架、组件库、是否移动端优先）
- 明确不做什么

### 2. 产出 `UI-SPEC.md`

必须包含七部分：

1. **设计令牌**：颜色（含语义色：背景/表面/边框/主色/危险色）、间距刻度、字号与行高、圆角、阴影、动效时长
2. **布局与栅格**：断点、容器最大宽度、页面密度
3. **页面结构线框**：ASCII 或静态 HTML，标出区块层级
4. **组件清单**：用到哪些组件，各自职责
5. **状态矩阵**：见下一节
6. **文案与极端情况**：空状态、错误态、加载态、超长文本、无权限
7. **验收清单**：每条都能用截图或工具验证

### 3. 组件状态矩阵

每个交互组件必须逐项列出，做成表格：

| 状态 | 表现 | 说明 |
| --- | --- | --- |
| default | | |
| hover | | |
| focus-visible | | 键盘可达，不能只靠颜色 |
| active | | |
| disabled | | |
| loading | | |
| empty | | |
| error | | |

只做了 default 和 hover 的组件，视为未完成。

### 4. 实现与验证

1. 先实现**静态骨架 + 令牌**，不接业务数据
2. 再用真实数据填充，逐块替换占位
3. 在 **375 / 768 / 1440** 三个宽度下截图
4. 对照 `UI-SPEC.md` 逐条勾选验收清单
5. 检查视觉一致性：对齐、间距节奏、字重层级、对比度

## 反模式

- 紫蓝渐变 + 居中大标题的“AI 默认页”
- 间距只有 8 和 16 两档来回用，没有节奏
- 只做桌面断点，移动端靠缩放
- 只有 happy path，没有空 / 错 / 加载
- 图标风格混用（emoji、线性图标、实心图标）
- 正文对比度不足 4.5:1
- 用 `!important` 打补丁
- 交互只用颜色表达状态（色盲不可用）

## 交付物

- `UI-SPEC.md`
- `tokens.css` 或 `tokens.json`
- 375 / 768 / 1440 三张截图
- 验收记录（逐条打勾或注明未达成原因）

## 与其他技能的关系

- `to-spec`：把 UI-SPEC 的关键决策引用进规格，不要把整份规范抄进去
- `to-tickets`：UI 工单也要垂直切片，切片里必须包含对应状态
- `implement`：先骨架后数据；骨架阶段就要接令牌
- `code-review`：在规范轴里增加“视觉一致性”检查项
- `retro`：如果多次出现同类视觉问题，把它变成 lint 规则或模板，而不是反复口述
